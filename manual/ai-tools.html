AI tools (optional)

Sensible ships no AI client, no provider account and no model. This chapter explains what each candidate tool is for, what it sends off this machine, and how to install, update or remove an optional client yourself.

Before you start

~/ and $HOME mean your home directory, so ~/Downloads is the Downloads folder inside it. $USER is your login name. PATH is the list of directories your shell searches for commands; adding a directory to it makes commands there available by name. Leave a leading ~ outside quotation marks. A line beginning with # is a comment, and sudo runs one administrative command.

Every recipe in this chapter needs internet access, and every one of them is a deliberate choice you make after installation. Sensible adds no AI client, no vendor repository, no model weights and no background service. If you skip this chapter entirely, nothing in the image changes.

Installing a client is not the same as using one

These programs are clients. In their documented default configuration they send your prompts to a provider's service and display the replies; a client you point at a local runtime instead never leaves this machine. Every recipe in this chapter documents the remote route, because none of them installs a local runtime or a model for you. Four separate things are easy to confuse, and this chapter keeps them apart:

  • The client is the program you install. Some clients are open source; that says nothing about the service they call.
  • The model runs on the provider's computers and is billed per token unless you deliberately add a local runtime. Installing an open-source client does not make the model open source, free, private or offline, and it does not give you a local one.
  • The account is the provider's sign-in, and API billing is a separate account at the provider's developers' site. A chat subscription normally does not pay for API use, and an API key does not give you the chat app.
  • Offline installation is only the download. As documented here, every prompt still needs a network connection; only a separately installed local runtime changes that.

Installing nothing here needs an AI account: no recipe signs you in, and Sensible works exactly the same whether you install a client or not. Using the documented, cloud-backed setups does need one — either provider sign-in or an API account with a key, and usually both paid. The last paragraph of each entry says what was tried on Debian Testing, and what was not.

Permissions and untrusted code

A coding agent reads files, edits them and runs shell commands with your account's rights. Sensible does not sandbox these tools for you, and installing one does not make it safer. Treat every agent session as if a stranger were typing at your keyboard.

  • Run it as yourself, never as root. sudo opencode or sudo claude lets a mistake, or a poisoned prompt, act on the whole system. The Claude desktop app also refuses to start as root.
  • Keep approval prompts on. The agent clients here have a mode that skips asking before edits or commands. Use it only in a throwaway copy of a project, and switch it back when you are done.
  • Read the diff before you commit. Start from a clean Git repository, ask for one small change, then inspect it with git diff before keeping it. See Git.
  • A new project is not trusted code. Instruction files such as AGENTS.md, GEMINI.md, .cursorrules or .mcp.json can be committed by a stranger. An agent may read them as instructions, so review a repository before pointing an agent at it.
  • Plugins and MCP servers run code. They are third-party programs with the same rights as the client. Do not install one "to fix" an error message, and prefer tools you would recognise by name.
  • Nothing needs administrator access at run time. If a client asks you to run a command with sudo in the middle of a session, that is a reason to stop and read the command first.
A prompt can be an injection

Any file or web page an agent reads may contain text aimed at the agent, not at you. Sensible cannot detect that. If a client starts suggesting you run a command you did not ask for, close it and look at the file or page that mentioned the command.

Accounts, keys and billing

There are two ways to pay a provider, and they are not interchangeable.

  • Chat subscription: you sign in to a website or desktop app and pay a monthly fee for that app. Claude Code needs one of Anthropic's paid Claude plans; the free plan does not include it. A provider's API-platform account, such as an Anthropic Console account, is not a subscription even when the same vendor sells both.
  • API billing: you create a key on the provider's developers' site and are charged per token. A subscription does not normally include API credit, and API keys do not unlock the chat app. An API key is a payment instrument, not a login.

Ways to supply a key, in rough order of preference:

  • Browser sign-in (/connect in OpenCode, agy, codex, claude). Nothing is copied by hand, but where the client keeps the resulting token is client-specific, and several of them use a plain file in your home directory rather than the desktop keyring. Treat those files exactly like a saved password: do not commit them, paste them into a bug report or assume that removing the app removed them. The update and removal table lists the file for each entry.
  • The client's own key command, for example llm keys set openai, which prompts without echoing and writes a file in ~/.config/.
  • An environment variable such as GEMINI_API_KEY, set in the terminal for the current session. Storing a key in a file that ends up in a repository or a log is a leak, not a shortcut.

Never paste a real key into a command line, a screenshot, a chat message, a bug report or an example copied from a forum. A key on a command line stays in your shell history, and this manual never shows a real one. When a client offers a pipe instead — printenv OPENAI_API_KEY | codex login --with-api-key is the documented Codex form — prefer it. If a key leaks, revoke it in the provider's dashboard first and then create a new one.

Two clients keep their stored credentials in a readable file by default, and you can check either one yourself:

  • OpenCode writes API keys and OAuth tokens to ~/.local/share/opencode/auth.json.
  • Codex caches login details in plaintext at ~/.codex/auth.json unless you set cli_auth_credentials_store to keyring in its configuration, which then fails if no keyring is available. codex logout clears the stored credentials; codex login status shows the active method.
  • Antigravity CLI and Anthropic's desktop app document keyring storage instead, and the Claude desktop app needs an unlocked keyring to keep you signed in. See Saved passwords.

Every client here keeps something on this machine: prompts, transcripts or a local cache. LLM stores every prompt and answer in a local SQLite log by default and can be told to stop: llm logs off. Revoking a key does not delete what was already sent to a provider, and it does not delete local history. Remove a client's data directories when you remove the client.

Opening a vendor repository for updates means trusting that vendor with your package manager. That is why the update table says who updates what, and why Sensible's own images keep /etc/apt/sources.list.d/ to the distribution's own mirrors.

Desktop clients

Two vendors publish a desktop client for Linux, both still labelled a preview or a beta by their own documentation. Neither is part of the image; both are large downloads and both need internet and a vendor account.

The always-available alternative is the same service in a browser, using the browsers already described in Browsers & communication. Nothing in this section is required, and the browser route is the right first choice for occasional use.

ChatGPT desktop app

What it is: OpenAI's desktop client with Codex features, including working on local projects and files. It is a preview, not a finished Linux release.

Why considered: the documented route for using an existing ChatGPT plan from the desktop, including on a Debian system.

Before you install: OpenAI lists Ubuntu 24.04 and 26.04, Debian 13, Fedora 43 and 44 and current Arch, each for x64 and ARM64. Sensible is built on Debian Testing, which is not on that list. Other distributions "may work but aren't formally supported", so treat this as untested on this image.

Architecture: uname -m prints the processor architecture; x86_64 is x64 and aarch64 or arm64 is ARM64. OpenAI publishes a package for each, and APT refuses a package built for the other one, so download the matching file rather than the nearest name.

cd ~/Downloads
uname -m

# x86_64 machines
curl --fail --location --output chatgpt_amd64.deb \
  https://persistent.oaistatic.com/codex-app-prod/linux/deb/latest/chatgpt_amd64.deb
sudo apt install ./chatgpt_amd64.deb

# aarch64 / arm64 machines: use the ARM64 package instead
curl --fail --location --output chatgpt_arm64.deb \
  https://persistent.oaistatic.com/codex-app-prod/linux/deb/latest/chatgpt_arm64.deb
sudo apt install ./chatgpt_arm64.deb

Run only the pair that matches your own uname -m output. Install the downloaded file with APT, not by double-clicking it. Sensible is x86_64, so the first pair is the one exercised below.

What installation changes: the package registers OpenAI's signed APT repository at /etc/apt/sources.list.d/chatgpt.sources, installs its signing key at /usr/share/keyrings/chatgpt-archive-keyring.gpg, adds an AppArmor profile, and marks the repository as added in /etc/default/chatgpt. Installing the downloaded package again will not re-add a repository entry you deleted on purpose.

Launch: open ChatGPT from the application menu on GNOME or KDE, or run chatgpt in a terminal, then sign in with your ChatGPT account. Sign-in and billing are the vendor's; Sensible has no account and nothing is preconfigured.

Known limits from the vendor: no Computer Use on Linux, and native Wayland is experimental. Under Wayland the app uses XWayland when available; chatgpt --ozone-platform=wayland forces native Wayland, where window behaviour may be incomplete.

Updates: APT, through the repository the package registered. Run sudo apt update and then sudo apt install --only-upgrade chatgpt, or let your normal system updates bring it forward.

Remove: sudo apt remove chatgpt removes the program and its menu entry, but leaves the OpenAI repository entry, its keyring, the AppArmor profile and /etc/default/chatgpt behind. Delete those too if you do not want OpenAI's repository active. Only one of those two leftovers can break APT: a configured source whose signing key has been deleted makes every later apt update fail, while an unused key file on its own is harmless. Remove the repository entry first, then the key.

Sensible validation: on 2026-10-02 the download installed and removed cleanly on Debian Testing (package chatgpt 26.930.21537, roughly 1.5 GiB installed, dependencies resolved from Debian Testing alone). On 2026-10-03 its GNOME application-menu entry launched the installed app and the app initialized before being closed. KDE launch and the sign-in flow were not tested. Vendor Linux page

Claude desktop app

What it is: Anthropic's desktop app for Chat, Cowork and Claude Code, now in a Linux beta with an official APT repository. Earlier Sensible notes said no official Linux build existed; that is out of date, so verify the current vendor page before installing.

Requirements: a Debian-based distribution on Ubuntu 22.04+ or Debian 12+, x86_64 or ARM64. Other Debian-based distributions such as Debian Testing meet those requirements but are not officially tested. Only Debian-based distributions are supported today. The repository publishes no other architecture: if dpkg --print-architecture prints anything other than amd64 or arm64, stop rather than looking for another build.

Before you install: the repository is trusted through a signing key, and APT will only use it if you first fetch that key yourself. Download it, then read the fingerprint before registering the repository. gpg is not part of this image, so install it first; the file itself is only read by APT, and gpg is used here purely to display who signed it.

sudo apt install gnupg
sudo install -d -m 0755 /usr/share/keyrings
sudo curl -fsSL https://downloads.claude.ai/claude-desktop/key.asc \
  -o /usr/share/keyrings/claude-desktop-archive-keyring.asc

# Compare the printed fingerprint with the one below, then continue
gpg --show-keys /usr/share/keyrings/claude-desktop-archive-keyring.asc

echo "deb [arch=amd64,arm64 signed-by=/usr/share/keyrings/claude-desktop-archive-keyring.asc] https://downloads.claude.ai/claude-desktop/apt/stable stable main" \
  | sudo tee /etc/apt/sources.list.d/claude-desktop.list
sudo apt update
sudo apt install claude-desktop

The expected fingerprint is 31DD DE24 DDFA B679 F42D 7BD2 BAA9 29FF 1A7E CACE. If that line is missing, stop: a wrong key makes every later apt update fail with NO_PUBKEY BAA929FF1A7ECACE. The vendor also documents downloading the .deb straight from the repository, which carries the same key; installing it that way still registers the repository for later updates.

Try first: the browser. Claude in a browser needs no repository, no key and no extra packages, and on KDE it avoids the keyring problem described below.

Launch: open Claude from the application menu, or run claude-desktop, then sign in with your claude.ai account or your organization's SSO. A free account is enough for Chat; the Cowork tab needs a paid plan. The desktop app does not accept a Console API key; use Claude Code for API-key authentication.

KDE: a documented keyring caveat Sensible has not tested

Anthropic documents that the desktop app stores your sign-in in your desktop keyring, and that when KDE Plasma and GNOME Keyring are both installed it can report that your sign-in will not be saved even though KDE Wallet works. Sensible has not reproduced this on the KDE image, because KDE launch and sign-in were not tested here, so treat it as something the vendor warns about rather than a confirmed Sensible fault.

If you hit it, do not remove a system credential service on this image's say-so. Removing GNOME Keyring affects other applications that may use it, and Sensible has not tested the result. Follow the vendor's own troubleshooting for the message you see, use the browser route above while you sort it out, and only then consider a keyring change you understand.

Not in the Linux beta: Computer Use and voice dictation. Cowork, the tab for longer agent tasks, runs inside a virtual machine the app hosts with QEMU and KVM, so it needs hardware virtualization enabled in firmware, an unlocked /dev/kvm, your account in the kvm group (sudo usermod -aG kvm "$USER", then log out and back in), and the emulation packages for your own architecture — qemu-system-x86 and ovmf on x86_64, qemu-system-arm and qemu-efi-aarch64 on ARM64, plus virtiofsd on either. Check which you have with dpkg --print-architecture before installing anything. Chat needs none of this. Cowork also needs a paid plan, unlike Chat.

Updates: APT. The app does not update itself on Linux, so new versions arrive with your normal sudo apt update && sudo apt upgrade, or through your desktop's software updater.

Remove: sudo apt remove claude-desktop removes the app and any repository entry and key that its package registered. This recipe created /etc/apt/sources.list.d/claude-desktop.list before installing the package, so check whether it remains and remove it yourself if it does: sudo rm /etc/apt/sources.list.d/claude-desktop.list. Remove /usr/share/keyrings/claude-desktop-archive-keyring.asc too only when no remaining Anthropic repository entry uses it. Run sudo apt update afterward to confirm the repository configuration is healthy.

Sensible validation: on 2026-10-02 the key fingerprint verified, and the repository served claude-desktop 2.9939.4 for amd64 with dependencies resolving on Debian Testing (roughly 560 MiB installed, recommended packages include the QEMU set and a keyring). On 2026-10-03 its GNOME application-menu entry launched the installed app and the app initialized before being closed. KDE launch, package removal and the sign-in flow were not tested. Vendor Linux guide

Terminal clients

Each entry below gives the official route, a first task, who updates the installed copy and how to remove it. Three of the installers are shell scripts fetched from the internet, so each one is shown in three steps: download the script to a file, read it, then run that file. Piping a download straight into a shell starts executing it before the transfer has even finished, so a truncated or substituted download runs partly — which is why Terminal tools & recipes advises against the pipe form. Never run any of these with sudo: each installs files into your own home directory.

OpenCode

What it is: an open-source coding agent for the terminal, with the same engine also offered as a desktop app and IDE extension. It uses any provider you configure.

Why considered: the first Sensible candidate for an open-source terminal agent, and the most flexible about which model provider answers.

Better fit when: you want one agent that can switch between providers, or you already use a subscription rather than a paid API key.

Install: the vendor's script installs a single binary into ~/.opencode/bin/ and adds that directory to your PATH in ~/.bashrc. Official alternatives are npm install -g opencode-ai, Homebrew and the GitHub releases, if you prefer a package manager. ~/Downloads in the recipe below is just a convenient place to keep the file you read; any directory you can write to works.

# 1. Download the installer to a file instead of piping it into a shell
curl --fail --location --output ~/Downloads/opencode-install.sh \
  https://opencode.ai/install

# 2. Read it before running it; press q to leave the viewer
less ~/Downloads/opencode-install.sh

# 3. Run the file you just read, as your own user
bash ~/Downloads/opencode-install.sh

# Open a new terminal afterwards, or reload your shell configuration
source ~/.bashrc
opencode --version

Launch and first task: change into a project directory, run opencode, then describe a small task. Tab switches between plan mode, which cannot change files, and build mode. /init writes an AGENTS.md description of the project, which upstream recommends committing to Git.

Accounts and keys: /connect starts sign-in. OpenCode's own curated model service needs billing details and an API key, which is API billing rather than a chat subscription; other providers can use their own keys. Whichever you choose, the token is written to ~/.local/share/opencode/auth.json, a plain file in your home directory — not to the desktop keyring.

Updates: the installer is the update owner — download and run it again to upgrade. Nothing in Debian supplies or verifies this binary.

Remove: run opencode uninstall, which lists what it will delete and asks for confirmation; upstream documents it as the uninstall path. Then remove the two opencode lines the installer added to ~/.bashrc, and delete ~/.local/share/opencode/ if you want the credentials, logs and stored sessions gone as well. ~/.cache/opencode/ holds downloaded provider packages and can be deleted too.

Sensible validation: the script installed and ran on Debian Testing on 2026-10-02 (version 1.18.34, roughly 180 MiB in ~/.opencode/). No provider was configured and no session was run. Upstream introduction

LLM

What it is: a command-line front end to language models, from the author of Datasette. It answers prompts, keeps a local log of them, and can be extended with plugins for more providers.

Why considered: the complementary tool to a coding agent: it prompts and pipes text, and it does not edit your project unless you ask it to. It is the only entry here Debian packages, and it needs no JavaScript runtime.

Better fit when: you want to script a model call, summarise text or translate output in a pipeline, rather than have an agent change files.

Install: use the Debian package, which APT updates and removes for you, or pipx for the newest upstream release in an isolated environment that leaves Debian's Python alone. Do not use sudo pip install: Debian's Python is managed by APT and belongs to the system.

# Route A: Debian package (simplest, updated with the rest of the system)
sudo apt install llm
llm --version

# Route B: pipx, isolated from the system Python
sudo apt install pipx
pipx install llm
~/.local/bin/llm --version

Launch and first task: llm plugins lists available models, llm keys set openai stores a key without echoing it, and llm "explain what a tarball is in two sentences" sends your first prompt. Everything runs in the terminal; there is no GUI to open.

Local data: prompts, answers, keys and preferences live under ~/.config/io.datasette.llm/. llm logs off stops prompt logging, llm keys path shows the key file, and llm logs status reports the current setting.

Updates: APT for the package, pipx upgrade llm for the isolated copy. Each has exactly one owner; do not mix them on the same account.

Remove: sudo apt remove llm, or pipx uninstall llm. Both leave ~/.config/io.datasette.llm/ behind, which is where prompts and keys are stored — remove it deliberately if you want them gone.

Sensible validation: both routes were installed and version-checked on Debian Testing on 2026-10-02 (Debian 0.36-1; pipx 0.36 with system Python 3.14.7 unchanged). No prompt was sent: Sensible configured neither a cloud provider nor one of the local-model plugins, so neither route was exercised. Upstream setup

Codex CLI

What it is: OpenAI's open-source terminal agent. It inspects a repository, edits files and runs the tools already on your machine, and it also runs non-interactively for scripts and CI.

Why considered: the terminal counterpart of a ChatGPT plan, and distinct from the hosted Codex service.

Better fit when: you want one agent from a single vendor, or you need codex exec in a repeatable pipeline.

Install: the official standalone installer keeps a launcher in ~/.local/bin/ and its releases under ~/.codex/, and adds ~/.local/bin to your PATH in ~/.profile. An npm install and Homebrew are also documented.

# 1. Download the installer to a file instead of piping it into a shell
curl --fail --location --output ~/Downloads/codex-install.sh \
  https://chatgpt.com/codex/install.sh

# 2. Read it before running it; press q to leave the viewer
less ~/Downloads/codex-install.sh

# 3. Run the file you just read, as your own user
sh ~/Downloads/codex-install.sh

# Open a new terminal afterwards, or reload the profile
source ~/.profile
codex --version

Launch and first task: run codex in a project directory and choose a sign-in method on first use, then ask it to explain the project before it changes anything. /init writes project instructions, /permissions sets what it may touch without asking, and /review reports problems in changes without modifying your working tree.

Accounts and keys: signing in with a ChatGPT plan is subscription access; an API key is separate billing. Choose deliberately, because the two behave differently. Either way the credential is cached locally: in plaintext at ~/.codex/auth.json, unless you set cli_auth_credentials_store to keyring in config.toml. Use printenv OPENAI_API_KEY | codex login --with-api-key rather than typing a key as an argument.

Updates: download and run the same install script again. That is the only documented update path for the standalone install.

Remove: run codex logout first, so the stored credential is cleared while the client can still act on it, and check codex login status afterwards. Then delete ~/.codex/, the ~/.local/bin/codex symlink, and the PATH line the installer added to ~/.profile. rm -f is safe on the symlink because it is not a directory.

Sensible validation: the installer ran and codex --version reported 0.160.0 on Debian Testing on 2026-10-02, with roughly 430 MiB under ~/.codex/. Sign-in and a real session were not tested. Upstream CLI page

Antigravity CLI

What it is: Google's current agent-first terminal client, written in Go. It is the successor to Gemini CLI, and it is what the Gemini CLI command name now leads to.

Before you install: Google replaced Gemini CLI for consumer accounts on 2026-06-18. Gemini CLI remains documented only for enterprise and paid Gemini API-key use; if that is your situation, the old gemini command is still installed from npm install -g @google/gemini-cli and removed with npm uninstall -g @google/gemini-cli. For everyone else it stops serving requests. Sensible read those two commands and did not run them.

Install: the official script places a single binary at ~/.local/bin/agy and does not edit your shell configuration. --skip-aliases also stops it removing any leftover agy shell alias, and --skip-path stops it touching your profile.

# 1. Download the installer to a file instead of piping it into a shell
curl --fail --location --output ~/Downloads/antigravity-install.sh \
  https://antigravity.google/cli/install.sh

# 2. Read it before running it; press q to leave the viewer
less ~/Downloads/antigravity-install.sh

# 3. Run the file you just read, as your own user
bash ~/Downloads/antigravity-install.sh

# If the command is not found, add it for future terminals
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc
source ~/.bashrc
agy --version

Launch and first task: run agy in a project directory. Sign-in opens your browser, or it reuses a session from your desktop keyring. /permissions and /diff are the two commands to know before letting it change anything.

Accounts and keys: browser sign-in is the normal route. A Gemini API key is API billing, needs GEMINI_API_KEY exported in the shell plus a modelProvider setting, and is meant for headless machines.

Updates: the installer is the update owner; download and run it again. /logout clears the stored session from your keyring.

Remove: delete ~/.local/bin/agy and, if you added the PATH line yourself, the matching line in ~/.bashrc. Configuration lives under ~/.gemini/ and is not removed for you.

Sensible validation: the script installed and agy --version reported 1.2.15 on Debian Testing on 2026-10-02 (roughly 200 MiB). Sign-in was not tested. Upstream install page

Aider

What it is: a terminal pair-programming tool that proposes edits as diffs and commits them to Git as you go, so you always see and can undo the history.

Why considered: the diff-first alternative to an agent that edits silently.

Better fit when: you want a tight Git-based loop and prefer to read every change before it is kept.

Install: upstream's recommended route is a two-step one, and it is the one that works here: install aider-install into an isolated environment, then let it create Aider's own private Python environment, fetching a compatible interpreter if your system Python is too new.

# Isolated, and Debian's own Python is left alone
sudo apt install pipx
pipx install aider-install
aider-install

aider --version

Why not the shorter commands: pipx install aider-chat installs Aider into an environment using your system Python, and Aider's dependencies do not always have packages for a brand-new interpreter. On 2026-10-02 it failed on Debian Testing for exactly that reason. Aider's own documentation also warns that distribution packages often install it with the wrong dependencies.

Launch and first task: in a Git repository, run aider and describe one small change. Watch the diff, and refuse anything you did not ask for. Aider commits each accepted change, so git log is your history and git reset --hard HEAD~1 undoes the last one.

Accounts and keys: Aider needs a model and a key for it. That is API billing. Choose the model with --model, and supply the key through an environment variable such as OPENAI_API_KEY or an untracked .env file in the project rather than on the command line: Aider also accepts --api-key provider=<key>, but that form puts the key into your shell history, which is exactly what the key hygiene rule above rules out.

Updates: pipx upgrade aider-install followed by aider-install again. It is the only owner of the Aider copy; do not also install the Debian or npm variant.

Remove: this route installs two separate things, and the order matters. aider-install puts its own copy of uv inside the pipx environment and uses it to create Aider in ~/.local/share/uv/tools/aider-chat, with ~/.local/bin/aider symlinked into it — and that uv is not on your PATH, so a bare uv tool uninstall fails with "command not found". Remove Aider first, using the copy inside the environment:

# 1. Remove Aider's own environment and the ~/.local/bin/aider symlink
"$(pipx environment --value PIPX_HOME)/venvs/aider-install/bin/uv" tool uninstall aider-chat

# 2. Now remove the installer that supplied uv
pipx uninstall aider-install

Those two steps were run in that order on 2026-10-03 as an ordinary, non-root user, and aider was gone afterwards. Two things still remain afterwards, and neither is removed for you: the private CPython 3.12 that aider-install downloaded into ~/.local/share/uv/python/ (about 112 MiB) and uv's download cache in ~/.cache/uv/ (about 572 MiB after one install). Delete those two directories yourself if you want the disk space back; check the contents first, because both are permanent deletions.

Sensible validation: installed on Debian Testing on 2026-10-02 and aider --version reported 0.86.2, with system Python 3.14.7 unchanged. The removal sequence above was then run on 2026-10-03 as an ordinary user, which is where the measured sizes and the missing uv on PATH come from. No model was called. Upstream install page

Claude Code

What it is: Anthropic's terminal coding agent. Its licence is not an open-source licence and refers to commercial terms, so Sensible treats it as an optional third-party tool rather than something to redistribute.

Accounts and billing: it accepts a Pro, Max, Team or Enterprise account, or a Console account. The first four are paid Claude plans, so your subscription covers the CLI; a Console account is Anthropic's API platform and is metered per token instead, which is API billing rather than a subscription. The free claude.ai plan does not include Claude Code. A third-party provider such as Amazon Bedrock or Google Cloud's Agent Platform is a further route with that provider's own API billing.

Better fit when: you already have an Anthropic subscription and want the same agent in the terminal as in the desktop app.

Install: choose the update behaviour you want first. The APT route below is recommended because the client's own background updater does not apply to it and APT keeps one update path; the native installer updates itself in the background, which is convenient but means the client, not APT, decides when it changes.

# The key file is used by APT; gpg only reads it to show the fingerprint
sudo apt install gnupg
sudo install -d -m 0755 /etc/apt/keyrings
sudo curl -fsSL https://downloads.claude.ai/keys/claude-code.asc \
  -o /etc/apt/keyrings/claude-code.asc
gpg --show-keys /etc/apt/keyrings/claude-code.asc

# Then register the signed repository and install
echo "deb [signed-by=/etc/apt/keyrings/claude-code.asc] https://downloads.claude.ai/claude-code/apt/stable stable main" \
  | sudo tee /etc/apt/sources.list.d/claude-code.list
sudo apt update
sudo apt install claude-code
claude --version

The expected fingerprint is 31DD DE24 DDFA B679 F42D 7BD2 BAA9 29FF 1A7E CACE. The native alternative downloads https://claude.ai/install.sh — follow the same download, read, then run steps as the terminal clients above rather than piping it — and installs under ~/.local/, self-updating; claude doctor reports install health and whether auto-updates ran.

Launch and first task: run claude in a project directory and complete sign-in in the browser it opens. Ask it to read a file before it writes one, and treat every proposed command as a command you would run yourself.

Updates: APT for the APT route (sudo apt upgrade claude-code), or the client's own updater for the native route.

Remove: sudo apt remove claude-code, and then delete the repository line and the key file yourself — APT does not remove them, and a leftover deb line pointing at a missing key makes every later apt update fail.

Removing an optional client completely

Removing the program is only the first step. Each entry above lists what stays behind, and the leftovers fall into three kinds: a repository APT will keep contacting, a stored credential, and a local record of your prompts. Work through the matching entry, then check the result:

# Review the repositories APT is currently configured to use
grep -r . /etc/apt/sources.list.d/ | less
# Press q inside less when you have finished reading.

# Review what an optional client left in your home directory
ls -a ~/ | grep -E "opencode|codex|gemini|pipx|local"
ls -a ~/.local/share/opencode/ ~/.codex/ ~/.config/io.datasette.llm/ 2>/dev/null

Deleting a keyring entry or a configuration directory is a permanent deletion, so look at the contents first. Keep the ordering in mind: remove a repository entry before its key: a source left configured without its key is what breaks APT, not an unused key.
